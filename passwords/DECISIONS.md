## [verify] results that changed the design

| Plan said | Found | What we do |
|---|---|---|
| `setAccessLevel` for `storage.session` in both engines | Not implemented in Firefox; Chrome takes an object. The default is already trusted-contexts-only in both. | Don't call it. E2E test that a content script can't read `storage.session`. Never put keys in `storage.local`. |
| `passkeys.directory` as a source | Run by 1Password, all rights reserved, no API. | Use `passkeys-api.2fa.directory/v1/*.json` (CC-BY-4.0) and `api.2fa.directory/v4/*.json` (MIT, attribution required when shown). |
| `chrome.dom.openOrClosedShadowRoot` in Firefox | Not on `browser.dom`. Firefox has `element.openOrClosedShadowRoot`. | Use both with fallback. |
| Windows passkey provider "availability unclear" | GA since Nov 2025, but needs package identity (MSIX or sparse). | Stays L: a plain Tauri NSIS install doesn't qualify. Extension passkeys cover Windows browsers. |
| Playwright `--load-extension` on Chrome-branded builds | Removed in 137. Playwright's Chromium keeps it; Playwright says Edge removed it too. | Extension E2E on Playwright Chromium. Edge tried once, reported honestly. |
| Selenium `installAddon` | Deprecated; use `installWebExtension(path, {permanent:false})`. | Use the new call. |
| Firefox MV3 background | No service worker; event page via `background.scripts`. | One background module that survives both lifecycles. |
| Windows Hello as key wrap | No documented stable secret. | DPAPI wrap plus user consent gate, documented as a convenience gate, not crypto. |
| HIBP through a server proxy | Keyless, no rate limit, padding supported; CORS allows direct. | Keep the proxy as the plan says, so the provider sees the server's IP. |
| Android autofill timeout | No documented figure. | Answer from a local index with no network or unlock. Measure and report. |
| Chrome 142 permission model | Norton's statement only; nothing from Google. | Use the documented setting, intent and content provider. Owner checklist covers real phones. |

## Build decisions

| # | Decision | Why |
|---|---|---|
| D1 | Isolated stack in `passwords/stack/` is its own compose project, not an override of the main file. Own images (`promptly-pw-backend:local`), own generated secrets in `passwords/stack/.env`. | An override can't remove `env_file: .env` or the `promptly-backend:local` tag, and rebuilding that tag would disturb `main`. Also means the owner's real secrets aren't used for test runs, so the copied `.env` the plan allowed was deleted from the worktree. |
| D2 | `backend/app` is bind-mounted in the isolated stack, and `frontend/dist` is served from the worktree. | Saves a 3 GB image build per change. A real image build happens before release checks. |
| D3 | Vitest (3.2.4) for vault core tests. | The repo had no unit runner for frontend. 3.x supports Vite 5. Runs in Node, with no stack. |
| D4 | Client-generated UUIDs for accounts, vaults and items. | AAD binds to them, so they must exist before the first encryption, and offline creation needs them. |
| D5 | Sealed boxes are signed by the grantor (added beyond the plan). | A sealed box alone lets a hostile server hand out a vault key it knows. |
| D6 | KDF ceiling as well as a floor (added beyond the plan). | A hostile server could otherwise hang clients with absurd parameters. |
| D7 | Argon2id floor 64 MiB, t=3, p=1. | Well above OWASP minimums. Same as RFC 9106's second option except p, because WASM is single-threaded. |
| D8 | `auth_key` verifier is HMAC-SHA256 with a random salt. No slow hash on the server. | `auth_key` is a 256-bit HKDF output, so a slow hash adds nothing. |
| D10 | No `pw_changes` table: delta sync reads `pw_items.revision` and keeps tombstones in `pw_items`. Added `pw_sessions`, `pw_connects`, `pw_settings`. | One less table to keep in step; the plan's table list was a guide. |
| D11 | Playwright's Firefox and full Chromium builds don't start on this machine (Windows "side-by-side configuration is incorrect"; only its headless shell and WebKit run). Installing runtimes is a hard stop, so: the web vault's Firefox tests run on the real installed Firefox (159) through Selenium and geckodriver, which is a stronger test anyway. | Listed in OWNER_STEPS. |
| D12 | Extension E2E runs on the real installed Chrome (156) through the DevTools `Extensions.loadUnpacked` call with `--enable-unsafe-extension-debugging`, because that build of Chrome ignores `--load-extension` (confirmed by the [verify] check) and Playwright's Chromium won't start here. Throwaway profile each run. | Tests the real browser. |
| D13 | A small manifest generator on esbuild instead of WXT, though WXT is maintained. | WXT is still 0.x with a large dependency tree; a password manager should ship as few moving parts as it can, and the two manifests are about 40 lines. |
| D14 | Extension pages and the background share one IndexedDB copy, so they tell each other when it changes (`sync` and `vaultChanged`) and re-read it. | Each holds its own decrypted index, and a pull in one wouldn't otherwise reach the other. |
| D15 | A test build differs from a release build in exactly: `host_permissions` granted up front (Chromium has no way to click its prompt), the popup can be aimed at another tab with `?tab=`, and Firefox's opens its own page on install (WebDriver can't navigate to one). | Listed so nobody assumes more. Firefox walks the real permission path, by Firefox's `extensions.webextOptionalPermissionPrompts` test pref. |
| D16 | Passkeys: conditional (autofill-style) `get` requests pass straight to the browser's own UI, and aren't offered in our inline menu. A modal `get` or a `create` shows our window, with the browser's own passkeys one click away. | Keeps a page from silently learning anything, and the wrapper small. A known limit: see REPORT. |
| D17 | User verification is reported true for passkeys when the vault's unlocked and the person confirmed in our window; items marked reprompt ask for the master password first. | Same model as other managers. Android asks for a biometric as the plan says. |
| D18 | The classifier gets its accuracy from the corpus it was tuned on, so that number flatters it. A second, separately written hold-out set gives the honest number, recorded before any fix is made from it. | See REPORT. |
| D19 | Hold-out history, kept as it happened. First blind run of `test-sites-holdout` (Chromium, before any fix): **41/60, 68.3%; positives 29/48; negatives 12/12; one honeypot flag**. I then read the failures, so that set is spent. After generic changes it scores 56/60 (93.3%), but that's a tuned number now, not a blind one. Harness changes made at the same time: a separate sign-up form on a two-panel page no longer counts as a honeypot hit unless it's the form chosen, and a name or company on a sign-up form no longer counts as an extra. A second set, written fresh by a new agent, gets scored once at M12 with no fixes after. | The gap between tuned and blind is the honest measure of how the classifier generalises. |
| D20 | Secure Send lives at `/passwords/send/<id>#key`, not the plan's `/s/…`. | The main app already uses `/s/:token` for share links. |
| D21 | Send password: Argon2id output goes through HKDF twice, one output as the proof the server checks, one mixed into the key. The spec's first draft used the Argon2id output for both. | What the server sees must not be able to open anything. CRYPTO_SPEC section 10 is updated. |
| D22 | Emergency access is per-vault grants, sealed and signed by the grantor's client, re-wrapped at each sync if a vault was added or re-keyed, and turned into view-only memberships when the wait runs out. The server reports someone else's personal vault as `shared`, so no client can mistake it for its own. | Reuses the member and grant code the whole client already verifies, and rotation already handles taking it back. |
| D23 | Mail codes: the client fetches recent codes and compares sender to site itself. The page's domain is never sent, which is stricter than the plan (it allowed sending it on click). | There's no need for the server to learn it. |
| D24 | Rooms and Mail Send posting takes a link and writes its own message, and refuses anything that isn't a link to that Send. | Makes "plain text into Rooms or Mail is impossible" true at the API, not just in the UI. |
| D25 | Windows app: all traffic goes through a Rust proxy that only reaches the connected server's `/api/passwords/`, refuses redirects and adds the device token, rather than CORS or `tauri-plugin-http`. The page has no network of its own. | The page never holds the token, and CSP can block `connect-src` outright. |
| D26 | Windows app runs two vault clients per page (the screens and a background shell for quick search, backup, SSH), as D14 does for the extension. Its offline copy is `IdbStore` in the WebView2 profile, not a separate app data file. | Same core, same tests. The disk scan covers the profile. |
| D27 | WebView2 general autofill is off, because it wrote form values, including the Secret Key, to `Web Data` in plain text even with `autocomplete=off`. `freezePrototype` is off: with it on, a bundled dependency throws at load (not identified). | Found by the disk scan. Chrome's behaviour for web and extension pages is checked at M12. |
| D28 | Hello is only offered on the Unlock screen once it's been turned on here and the host still has it. The Settings box has its own password field. | It used to show whenever the platform had it, and read a field further down the page. |
| D29 | Short PIN: the extension keeps it in `storage.session`, and the desktop app in process memory. Both go when the browser or app closes, and five wrong tries wipe it. Web has none, since a page reload would lose it anyway. | Plan 3.5 asks for extension and desktop. |
| D30 | Passkey PRF unlock is web only, and offered after a real create and get has worked on this browser. | An extension origin isn't a usable RP ID across browsers. Never the only way in. |
| D31 | Travel mode keeps the vault's row and drops its items and its sync on this device; turning it off asks for the master password. It doesn't change what the server holds. | Says what it does and doesn't protect on screen. |
| D32 | Security email watch and mail codes need the `mail_codes` device scope. Extension and desktop ask for it at connect; extension filling is still off until the setting's on. The Windows app uses it for the Security check only. | Separate from `vault`, as the plan says. |
| D33 | Second blind set (`test-sites-holdout2`, written fresh with no sight of the classifier), scored once on Chromium, before any fix: **38/60, 63.3%. Positives 29/48. Negatives 9/12. False fills 4** (three negative pages offered to fill, and one honeypot chosen). On the same day the tuned set scored 161/161. From the scorer: username and email count as one answer, since a login's identifier fills the same either way (decided before scoring). This set is now spent too. | The honest measure, and well below the 95% target. Reading the failures to improve the classifier means any number on this set afterwards is tuned, not blind. |
| D34 | The public-site smoke found a bug no fixture had: the classifier searched CSS class names as text, so utility classes like `min-h-10` and `max-w-md` made it reject the password box on real pages (Pinterest, Kraken). Classes now count only as a positive hint and never as a reason to reject. | Fixtures don't have real sites' CSS. Worth more test pages from real markup patterns. |
| D35 | Sync pages couldn't split a revision: one batch or rotation gives many items one revision and clients carry on from the last one seen, so a page boundary inside it lost the rest on that device for good. Found by the 5,000-item test (4,200 arrived). The server now extends a page to the end of its revision. | A data-loss bug below the size every earlier test used. |
| D36 | On-click mode removes the passkey wrapper as well as the fields script, so WebAuthn is the browser's alone there. The wrapper waits 750 ms for the bridge to answer, and 6 minutes for a result once it has, then hands over to the browser's own API. A page can forge those answers only to fool itself. | Plan 6.6 and 4: fallback to the browser must always work. With no standing site access there's nothing to bridge through, and a page loaded before the mode changed can't be reached. Settings says so. |
| D37 | `clipboardRead` is optional and off. A box in This browser settings asks for it. Without it a clipboard due for clearing is cleared whatever's on it, because there's no way to tell. With it, something else on the clipboard is left alone; an empty or failed read counts as can't tell. | Plan 7, smallest set of permissions: "read data you copy and paste" is a heavy thing to ask of everyone, for what's only a courtesy. Taking it the other way round would let copied codes linger. |
| D38 | Clipboard timing: an alarm, because the worker dies, plus a timer for the exact time while it's alive. An extension API call every 20 s keeps it alive for that wait. Alarms don't fire sooner than 30 s on Chrome and 60 s on Firefox, so if the worker's killed during a 5 s setting it clears at the floor. Locking clears straight away. A browser that closes first leaves it there. | The schedule has to survive the popup closing and the worker dying. Nothing can run after the browser's gone. |
| D39 | Fetch and XHR results come from the page's Resource Timing entries, read in the isolated world. No `webRequest` permission and nothing patched in the page. Only after a person typed in a password box. 400, 401, 403, 422 and 429 after a submit mean failed; 2xx and 3xx mean a form that goes was a submit. A form that goes with no good request behind it, or that another password box replaced, isn't one. Status 0 (cross-origin without CORS) says nothing. | Plan 6.4 and the brief: no MAIN-world secrets. `webRequest` would wake the worker for every request on every site. A closed dialog or a Register tab shouldn't ask to save. |
| D40 | Generated passwords: a sign-up is saved at once with the tag `unconfirmed sign-up`, and a change sets `pendingPassword` on the existing login. The save offer after a successful submit finishes that item: username in and tag gone, or the pending password committed. That also applies on a "never" site, since the item already exists. Generating again on the same origin reuses the waiting item. With several logins on a change form, the menu asks which. Someone who can't edit a shared login gets a login of their own. | Plan 6.4: a failed submit can't lose it, and one sign-up is one login. |
| D41 | Rules pack: `rules/pack.json` and a detached `rules/pack.sig` ship inside the extension, and the only update path is an extension release. The public key is pinned in `src/rules-key.ts`. A release has no key until the owner adds one, and then applies no pack and says nothing. A test build has a throwaway key, kept out of release bundles by the build. Rules with any field beyond the six known ones are refused, and so is a version older than one already seen. A person's taught rule always wins. | Plan 6.5. Selectors are data, and what they find still passes the fill guard. Note the signing input's fields are 16-bit length prefixed, so a pack can't pass 64 KB, well short of the 5,000 rules `openSignedPack` allows. `sign-pack.mjs` says so if it happens. |
| D42 | 2FA code after sign-in: nothing's copied at the fill. It's decided on the next page, about 1.2 s after it draws: only once the password's been filled, and only if no frame has a password box or a code box. Once per flow, with a short note on the page. Never for a fill-only member. The popup and menu put the flow's item first. | Plan 6.3. At the email step there's nothing to copy for yet, and a page with a code box should get the code filled there. |
| D43 | Filling across frames. Cards and identities: every frame with a box for the item, one at a time, each given only the values for its own boxes. Every origin other than the top page's is named in the one confirmation. Logins: the first frame as before, and then only frames that pass with no prompt (exact host of the item, same site as the page) and only for boxes the first doesn't have. Looser frames are skipped silently. An inline pick fills the frame its menu is in and no other, and fill on load the top frame only. | Plan 6.6's iframe rules, and "cards never from one inline click". In on-click mode `activeTab` doesn't reach cross-origin frames, so hosted card fields need all-sites access. |
| D44 | IntersectionObserver v2, in Chromium: at a menu click, no reading yet counts as not visible, and a false reading refuses it. Filling in a frame also reads each box, and refuses one still reading false after 500 ms, since a frame in another process reads false at first. A background tab reads nothing, so there it adds nothing. Firefox hasn't got it, and there a parent hiding a whole same-site frame still isn't seen. | It's the one check that sees a parent frame's styles. The popup and on-click mode are the answer on Firefox. |
| D45 | A code from a lookalike sender, or any code on a page that looks like a saved site, takes a warning first, with "Don't fill" on top and a second button that ignores clicks for 600 ms. A lookalike's sign-in link has no row. The background refuses both as well as the menu not offering them. | Plan 5.1 and 5.13. A link goes somewhere at once and can't be taken back, so it isn't offered at all. The page case goes beyond the brief: a real code on a phishing page is the worse one. |
| D46 | Lock on sleep covers `idle` reporting locked and a gap of over 3 minutes between 30 s alarms, because Firefox doesn't report locked. Turning the setting off stops both. A vault page locked from elsewhere reloads, back to its locked screen, since it holds keys of its own. Auto-lock reads the Settings screen's values from the store. `Settings.fillOnClickOnly` is unused: the extension's own setting decides, and the vault page writes that whole object back from memory. | Plan 3.5. |
| D47 | Further test build differences, on top of D15: `clipboardRead` granted on Chromium, a blank `test.html`, a `test` message for hooks (`handleTest`, dropped from release bundles and checked by a test), plain `http` for fill on load on `localhost` and `*.localhost`, and a throwaway pack key. `--minify` on a test build times a popup of release size. | Listed so nobody assumes more. Also the `test` hooks `flags` and `pending`. |
| D48 | Third blind set (`test-sites-holdout3`), written fresh, scored once on Chromium after the classifier work: **54/60, 90.0%. Positives 44/48. Negatives 10/12. False fills 3** (a modal's newsletter box chosen, and two negative pages offering to fill). From the scorer, decided before scoring: a lone password box counts the same as `signin` or `password-next`, since it fills the same. First blind runs in order: 68.3%, 63.3%, 90.0%. Tuned set: 161/161. Target was 95% with no false fills, so it isn't met on a blind set. Fixes after this score aren't reflected in that number. | The honest figure for how it does on forms it hasn't seen. |
| D49 | Reviews changed earlier decisions: D44 and D45 no longer hold. Firefox's inline menu doesn't fill or save, because it has no IntersectionObserver v2 and no other reading the page can't fake; the toolbar popup does it there. Lookalike rows are gone, not warned about. | A trustworthy visibility reading is the whole defence, and only Chromium has one. A real loss of convenience on Firefox. |
| D50 | User verification is reported only after a master password or PIN in the passkey prompt. `required` sites ask every time; `preferred` ones get UV=false. A passkey request with no gesture goes to the browser's own UI. | Saying UV happened because a vault was unlocked earlier was false. |
| D51 | A login saved with no port matches that scheme's default port only. Updating a saved password needs an exact host. Prefix mode compares origins first; regex must cover the whole origin. | Each one was used to fill or overwrite something on the wrong host. Self-hosted services on custom ports need their saved address edited. |
| D52 | Rotation is two steps: `DELETE member` cuts access at once and flags the vault; re-encrypting follows and can be retried. The flag shows as a Change the key prompt. | One atomic request meant a hostile member could stop themselves being removed. |
| D53 | Signed member lists weren't built. Grants are checked against people this person chose to trust, not against a list signed by the vault's managers, so a trusted member working with a hostile server can still hand out a vault key they know for a vault they're in. Keyset rotation wasn't built either. | Both are big changes to every client. Stated in SECURITY.md rather than hidden. |
| D54 | The local keyset check runs on every online unlock, and `wrapped_keyset` is returned by prelogin, to any signed-in session. | It needs the master password and the Secret Key together to be useful. It's what stops a forged device payload making `auth_key` a password oracle. |
| D55 | The isolated stack bind-mounts `backend/app` but doesn't reload it, so a backend fix isn't live until `docker restart PromptlyPw-Backend PromptlyPw-ArqWorker PromptlyPw-MailWorker PromptlyPw-MediaWorker`. It hadn't been restarted for a while late in M12, and everything run on the stack after that restart is what REPORT quotes. | Found as timeouts on a picker that needed a server fix already in the code. |
| D56 | `passwords/stack/docker-compose.full.yml` adds what the main e2e suite needs: media worker, tusd, photos-ml (read-only public model files from the main checkout's data folder) and a Maps stub. The stub only says a map exists, so the screen opens; there's no real map data and those tests mock the rest. The dev stack wasn't used. | The first main e2e run had 31 failures, all from services the isolated stack didn't have. A real map build takes about an hour and 15 GB. |
| D57 | A code audit against the plan, near the end of M12, found Must and Should features missing or partial, mostly on Android. Those were built after it, so anything quoted from before that point in REPORT is marked as such. | Done means every Must and Should, and earlier milestones had been called done without a row-by-row check. |
| D58 | Email codes and links also appear in the extension's toolbar popup. That's the only way in on Firefox and in on-click mode. Rows are worked out per frame from that frame's own address, a code goes only to a frame the sender belongs to, and a link needs a second click with "Don't open it" first. | D49 took the inline menu's filling away on Firefox, which left the setting on that browser doing nothing. A page can't cover the toolbar, so no visibility check is needed there. |
| D59 | Windows: typing a login copies its 2FA code afterwards, and Ctrl+Alt+Enter types the code alone. Neither for a fill-only member. | Plan 2FA row: copy the code after autofill, and fill it on the 2FA page. Auto-type is Windows' only autofill path. |
| D60 | Attachments over 32 MiB go straight to a file on Chromium through `showSaveFilePicker`. Firefox and WebKit still hold the whole file in memory, since they have no such API. | The plan says streaming. A page can't do better on those two without a service worker download trick. |
| D61 | "Export my library" gets its own step for the vault: a button to the vault's export screen, where the device makes the encrypted copy. It can't be inside the library job. | The main app holds no keys, and the job runs on the server. The plan's "no server plaintext" rules out anything closer. |
| D62 | Bookmark sync, asked for by the owner mid-build and not in the plan. One encrypted system item per bookmark, personal vault only, and a state comparison instead of an event log. Details and limits in BOOKMARKS.md. | Per-item gives the existing sync its conflict handling and delta paging for free. Comparing states means a browser that was shut catches up. A single blob would rewrite everything on every change. |
| D63 | `mergeDuplicates` on web listed a dropped copy's attachment on the kept item, but chunks are bound to the item they were uploaded on, so the file stopped opening and was deleted when the copy was purged. It now seals the file again under the kept item before changing anything. A reprompt on any copy also carries over. | Found by the Android work, from reading the code. Real data loss. |
| D64 | The toolbar popup is now a five-section panel (Vault, Codes, Generator, Bookmarks, More), at the owner's request after trying it. It reads item fields from the background one at a time through the same gates as before: `secretField` won't give a password to a fill-only member, or before a reprompt. Lists stay behind categories rather than showing the whole vault on open, so filling on a phishing page still starts from a short list. | "Similar to Bitwarden, ideally better." The extras: live 2FA codes, bookmarks and email codes in one place. |
| D65 | Set up in the popup offers the address of the page in front, only if its path is `/passwords` or a sign-in on the way there, and only as a value shown on the next screen to check. A page can't connect itself. | Owner signed in on the web and the extension still said to connect. A page saying it's Promptly proves nothing, which is why there's still a click and a visible address. |
| D66 | Replaces part of D16, at the owner's request. A quiet (conditional) `get`, and a `get` with no user activation, now run the browser's own request and also register an offer. An offer opens nothing. It shows in the toolbar panel, on the badge, and in the on-page menu on Chromium, and only a person choosing it opens the usual passkey window. Our answer aborts the browser's request. Whether a passkey exists reaches the page only if someone chooses one. Offers keep to the sender's real origin, the RP ID check, and only that frame's document, and go when the page navigates or aborts. | Passkeys that couldn't be reached looked broken. D44's reasoning for no window without a click stands, so the rule holds: no click, no window. The browser's prompt can show at the same time, since it can't be held back without losing the fallback the plan requires. |
| D67 | Passkey ids from another manager are converted to what sites use, at import and at use, since vaults already hold unconverted ones. Bitwarden writes a GUID, meaning its raw 16 bytes in written order, or `b64.` and base64url. | Found while building D66. Every passkey imported from Bitwarden would have matched nothing, and answered with the wrong id. Android has the same gap until its importer work lands. |
| D68 | Second-round review of the extension and web changes (see REPORT): the worst was on Firefox, which can't address a message to a document. An approved passkey answer could land in a page navigated into that frame after the window opened. Fixed three ways: a navigation closes the window, the offer's re-read before signing, and the answer must carry a value only that document's content script holds. Also: offers are validated and capped, `gunzipLimited` really limits memory, long bookmarks stay put, deletions count over a day with a Restore, a yes covers only the number shown, and Ctrl+Alt+Enter was never allowed through on Windows. | Each traced by reading, and fixed with a test where one's possible. |
| D69 | Emergency keys are sealed only to a contact whose safety words have been compared (`verified` in the trust book), on every client. Add asks first, and a row without it says so. Sharing stays trust on first use. | Found by the second-round Android review, and the web had the same gap. Emergency sealing hands over every key to your own vaults, so trust on first use wasn't enough. It's the one place this is required: the plan's TOFU stands for ordinary sharing, and SECURITY.md says what that leaves. |
| D70 | Bookmarks: Chromium refuses its Mobile folder (id `3`) on a desktop not signed in to its own sync: `create` and `getChildren` both say it doesn't exist, checked on Chrome 156 and Helium. So it gets a stand-in folder, as Firefox's menu does. | Without it, Firefox's Mobile bookmarks would land in Other on Chromium, and the next run would move them there for every browser. |
| D71 | Replaces D66's "no click, no window", at the owner's request after trying it on Google: Windows Hello came up instead of our window, and "just like Bitwarden" is what they want. A `get` with no click opens our window when the vault's unlocked and holds a passkey that request can use, it's the top frame, and that tab hasn't done it in the last 30 seconds. Otherwise it's the browser's, with the offer in the panel. `create` still needs a click. | The rule came from "a page could open as many as it liked". This keeps the limit that matters: only a site with a saved passkey can do it, and not repeatedly. The cost is that such a site can notice the window. Locked, there's no way to know whether a passkey matches, so the browser's prompt shows, and a page can't make every site open a window. |
| D72 | Changes D50, after trying it on Google: a site that only prefers user verification is now asked for it too, with Skip beside it. Before, it got UV=false with no question. Google then answered that the passkey was a "2-Step Verification only security key" and asked for the password.
